# maintainers protocol v1

**Status:** Draft. Targeting stabilization at v1.0 once the reference
implementation and at least one independent implementation interoperate.
**Versioning:** Semantic. v1.x adds optional fields and new envelope
kinds; v2 is a coordinated framing change.

## 1. Scope

This document specifies a protocol for declaring, renewing, and
transferring signing authority over a versioned artifact (typically a
git-versioned source repository, but adapters can target any
content-addressed store).

The protocol's goal: a project that adopts this protocol exposes,
inside its repo, a folder of signed envelopes from which any consumer
can determine, at any point in time, **who is authorized to sign
releases (or other tracked operations) on behalf of the project**, and
**which specific commits the current authority has endorsed**.

Non-goals:

- Identity of holders. The protocol identifies holders by Ed25519
  pubkeys. Display names and contact addresses (emails) are
  conventional but not load-bearing — verification operates on
  pubkeys.
- Real-time consensus. The protocol assumes the canonical log is
  append-only (git history). Conflicting writes are resolved by
  ordering in the log, with anti-equivocation handled by the storage
  adapter.
- Per-commit code review or in-line signing. The protocol endorses
  release commits as ranges over the intermediate commits; per-commit
  authorship signing (e.g., signed commits in git) is orthogonal and
  may be layered on top.

## 2. Concepts

### 2.1 Mandate

A **mandate** is a time-bounded grant of authority. It has:

- a **holder** — one Ed25519 pubkey, the principal who may sign new
  artifacts during the mandate
- an **issuedAt** and **expiresAt** — the validity window
- a list of **successors** — pubkeys who, after `expiresAt`, may
  unilaterally issue new mandates
- the **signedBy** pubkey and signature — who signed this mandate
  into being

A mandate is **valid** when its `signedBy` was authorized to sign it
at `issuedAt`. Authority transitions through the verifier algorithm
in §4.

### 2.2 Track

A **track** is an independent timeline of mandates for a specific
purpose. Common tracks: `release` (signs ReleaseEndorsements), `ca`
(signs cryptographic bindings for the project's users — e.g., a
CA-style key), `ops` (signs operational advisories). Each track has
its own mandate sequence, its own approval rule, and its own holder.
The same pubkey may hold multiple tracks; this is permitted but
generally discouraged for scope separation.

### 2.3 Approval rule

Per-track, an **approval rule** specifies how many signatures from
which set of keys are required for a mandate or artifact to be
valid. Schema supports threshold semantics from day 1:

```
{ "kind": "threshold", "threshold": 1, "of": "anyAuthorizedSigner" }
```

The default `1-of-N` rule (one signature from any authorized signer)
is the simplest case. Tracks can be set to `2-of-{a,b,c}` (a specific
threshold among named pubkeys) once the implementation supports
multi-sig signature collection.

### 2.4 Key file

A **key file** binds a pubkey to a human-readable record (display
name, email, optional metadata). Key files are stored in
`.maintainers/keys/` (named by current email) and rotated by
self-signed updates that append to the key's email-history. Key
files are not authoritative for permission decisions — those operate
on pubkeys — but they are how humans render mandate ownership.

### 2.5 Release endorsement

A **ReleaseEndorsement** is a signed declaration that a specific
commit is a release, accompanied by the full list of intermediate
commits since the previous endorsement. The intermediate list lets
consumers verify the maintainer endorsed the *exact set of commits*
between two releases — defending against history rewrites,
post-merge injections, and hostile mirror tampering.

## 3. Envelope formats

All envelopes are canonical-bytes signed by Ed25519. Canonical-bytes
format follows the same conventions as the host project's protocol
package (`flagship/<purpose>/v1`-style tag prefixes in the Flagship
implementation; protocol-level binding for other implementations).

### 3.1 Mandate

```
{
  "kind": "Mandate",
  "version": 1,
  "mandateId": "<uuid>",
  "track": "<track-name>",
  "holder": "<pubkey-hex>",
  "issuedAt": "<RFC3339>",
  "expiresAt": "<RFC3339>",
  "successors": ["<pubkey-hex>", ...],
  "signedBy": "<pubkey-hex>",
  "signatures": [
    { "pubkey": "<pubkey-hex>", "sig": "<sig-hex>" },
    ...
  ]
}
```

Field constraints:

- `mandateId` MUST be a fresh v4 UUID; consumers reject duplicates.
- `expiresAt` MUST be strictly later than `issuedAt`.
- `holder` SHOULD appear in `successors` if the holder wishes to
  re-mandate themselves after expiry without external takeover.
- `signatures` MUST contain enough valid entries to satisfy the
  track's current approval rule at `issuedAt`.

### 3.2 KeyFile

```
{
  "kind": "KeyFile",
  "version": 1,
  "pubkey": "<pubkey-hex>",
  "displayName": "<string>",
  "currentEmail": "<email>",
  "emailHistory": [
    { "email": "<email>", "from": "<RFC3339>", "to": "<RFC3339|null>" }
  ],
  "metadata": {
    "photo": "<url|null>",
    "github": "<handle|null>",
    "role": "<string|null>"
  },
  "introductionMandate": "<mandateId>",
  "signature": "<sig-hex>"
}
```

The key signs its own record. `emailHistory` is append-only; the
current email always appears as the entry with `"to": null`.

### 3.3 EmailRotation

```
{
  "kind": "EmailRotation",
  "version": 1,
  "pubkey": "<pubkey-hex>",
  "fromEmail": "<email>",
  "toEmail": "<email>",
  "rotatedAt": "<RFC3339>",
  "signature": "<sig-hex>"
}
```

Signed by `pubkey` itself. Consumers apply by appending to the key's
`emailHistory` and updating `currentEmail`. The corresponding
`keys/<old-email>.json` is replaced with a redirect record:

```
{ "kind": "KeyRedirect", "renamedTo": "<new-email>", "renamedAt": "...", "signature": "..." }
```

EmailRotation events SHOULD trigger a yellow-level alert in consumer
UIs (e.g., browser extension banner) so observers can sanity-check
the rotation against expected behavior.

### 3.4 KeyIntroductionRequest

```
{
  "kind": "KeyIntroductionRequest",
  "version": 1,
  "pubkey": "<pubkey-hex>",
  "displayName": "<string>",
  "currentEmail": "<email>",
  "metadata": { ... },
  "requestedAt": "<RFC3339>",
  "signature": "<sig-hex>"
}
```

Signed by `pubkey`. A new keyholder who is not physically present
emits this to declare candidacy. The current mandate holder reviews
and accepts by including the corresponding KeyFile in the next
mandate's successors list.

### 3.5 ReleaseEndorsement

```
{
  "kind": "ReleaseEndorsement",
  "version": 1,
  "releaseId": "<uuid>",
  "semverTag": "<string, e.g. v0.2.0>",
  "commitHash": "<40-hex>",
  "previousReleaseId": "<uuid|null>",
  "previousCommitHash": "<40-hex|null>",
  "intermediateCommits": ["<40-hex>", ...],
  "intermediateMerkleRoot": "<32-byte-hex>",
  "endorsedNotes": "<string|null>",
  "issuedAt": "<RFC3339>",
  "signedBy": "<pubkey-hex>",
  "signatures": [{ "pubkey": "...", "sig": "..." }, ...]
}
```

Field constraints:

- `commitHash` MUST be reachable from the host repo's main branch.
- `previousReleaseId` is `null` only for the genesis endorsement.
- `intermediateCommits` MUST list every commit on the first-parent
  chain from `previousCommitHash` (exclusive) to `commitHash`
  (inclusive). Order matches the chain direction (oldest first).
- `intermediateMerkleRoot` MUST equal SHA-256 over the concatenated
  bytes of `intermediateCommits` (each as 20 raw bytes).
- `signatures` MUST satisfy the release track's current approval
  rule at `issuedAt`.

### 3.6 TakeoverAlarm (consumer-side derived, not signed)

When a consumer observes a mandate signed by a successor (rather
than by the prior mandate's holder), it derives a TakeoverAlarm
locally for UI purposes:

```
{
  "kind": "TakeoverAlarm",
  "project": "<repo-url>",
  "track": "<track>",
  "previousMandate": "<mandateId>",
  "newMandate": "<mandateId>",
  "previousHolder": { "displayName": "...", "email": "...", "pubkey": "..." },
  "newHolder": { "displayName": "...", "email": "...", "pubkey": "..." },
  "detectedAt": "<RFC3339>"
}
```

TakeoverAlarms are not stored or signed. They are presented to the
user with explicit accept/pause/investigate actions.

## 4. Verifier algorithm

Given a track's full ordered list of mandates `M[0..n]` from the
canonical log:

```
function currentAuthority(track, now):
  validMandates = filter M[i] where isValid(M[i], M[0..i-1])
  active = last m in validMandates where m.issuedAt <= now < m.expiresAt
  if active != null:
    return active.holder
  else:
    # No active mandate; track is "expired pending succession"
    return null

function isValid(m, priorMandates):
  if m.mandateId is duplicated in priorMandates: reject
  if m.expiresAt <= m.issuedAt: reject

  # Determine which mandate's signers/successors authorize m
  if priorMandates is empty:
    # Genesis mandate. Accept iff m is signed by a pubkey it itself
    # names (i.e., the holder signs its own genesis). Trust derives
    # from the user trusting the repo at all.
    if m.signedBy != m.holder: reject
    if !verifySignatures(m, m.signatures, {m.holder}, m.approvalRuleFromPolicy()): reject
    return true

  # Non-genesis: find the predecessor mandate
  pred = last prior valid mandate p where p.track == m.track AND p.issuedAt < m.issuedAt
  if pred == null: reject

  if pred.issuedAt <= m.issuedAt < pred.expiresAt:
    # m issued during pred's active window — only pred's holder can sign
    authorizedSigners = {pred.holder}
  else:
    # m issued after pred's expiry — any pred.successor can sign
    authorizedSigners = pred.successors

  return verifySignatures(m, m.signatures, authorizedSigners, m.approvalRuleFromPolicy())
```

Key properties of this algorithm:

- **Most-recent-valid-mandate-wins.** No grace window, no notice
  period, no override semantics. One rule.
- **First-after-expiry wins.** Two successors racing to take over
  after expiry are resolved by canonical-log ordering; the second
  one to land is rejected (its predecessor is the first takeover,
  which lists the second successor's pubkey in its own successors
  only if explicitly re-named).
- **Genesis is bootstrapped by trusting the repo.** A consumer who
  trusts the repo enough to clone it transitively trusts the
  genesis mandate. Subsequent mandates verify through the chain.

## 5. ReleaseEndorsement verification

For a consumer fetching a newer endorsement E' given a known-current
endorsement E:

1. Verify `E'.signatures` satisfy the release track's approval rule
   under the current authority at `E'.issuedAt` (per §4).
2. Confirm `E'.previousReleaseId == E.releaseId` and
   `E'.previousCommitHash == E.commitHash`.
3. Recompute `intermediateMerkleRoot` from `E'.intermediateCommits`
   and confirm it matches the field.
4. For each commit hash in `E'.intermediateCommits`:
   - Confirm it exists in the local git clone (`git cat-file -e`).
   - Walk `E'.commitHash`'s first-parent chain backward; confirm
     the walk visits exactly the commits in `intermediateCommits`
     in the documented order, ending at `E.commitHash`.
5. If any step fails: reject the endorsement; raise a chain-mismatch
   alert; do not advance the local "latest endorsed" pointer.

## 6. Storage layer

The protocol's envelope formats and verifier are storage-agnostic.
Implementations provide an **adapter** that maps:

```
StorageAdapter {
  read(path) -> Promise<bytes>
  write(path, bytes, signedEnvelope) -> Promise<ok | conflict>
  list(prefix) -> Promise<path[]>
  log() -> Promise<{path, modifiedAt, sha}[]>   // canonical ordering
}
```

Two reference adapters are defined:

- **Git adapter** (the default for public projects). `read` fetches
  raw content from the repo provider; `write` commits to a target
  branch via a backing token or user OAuth; `log` returns the
  commit history of the `.maintainers/` folder, providing canonical
  ordering.
- **Encrypted-blob adapter** (for private user-level use, e.g., the
  Flagship user-identity store). `read`/`write` proxy through an
  AEAD-encrypted blob at a known location, keyed by HKDF of a user
  secret. The storage backend sees ciphertext only; the verifier
  operates on the decrypted blob locally on the user's device.

The verifier algorithm is identical across adapters; only the
naming layer (emails vs device labels) differs in display.

## 7. Folder layout (Git adapter)

```
.maintainers/
├── README.md
├── policy.json
├── keys/
│   ├── <email>.json
│   └── <email>.json                 (may include KeyRedirect after rotation)
├── tracks/
│   ├── <track-name>/
│   │   ├── policy.json
│   │   └── mandates/
│   │       ├── <iso-timestamp>-<short-summary>.json
│   │       └── ...
│   └── ...
└── endorsements/
    ├── <semver-tag>.json
    └── ...
```

`policy.json` at the root names the schema version and the list of
tracks. Each track's `policy.json` declares its approval rule and
default mandate duration.

## 8. Security considerations

**Anti-equivocation.** Adapters that don't provide native ordering
(rare for git) MUST add a transparency-log layer. Git's commit
ordering is canonical and tamper-evident relative to the public
state; mirror divergence is detectable by commit-hash mismatch.
Daemons cache seen-mandates locally so a rewritten history is
detected by hash mismatch on next fetch.

**Key compromise mid-mandate.** If a holder's key is compromised
during an active mandate, the attacker has full track authority
until that mandate's expiry. Mitigations: short mandate durations
for high-sensitivity tracks; in-flight successor designation so a
takeover at expiry is possible; out-of-band community contact via
the holder's email to coordinate.

**Successor compromise pre-takeover.** If a successor's key is
compromised, the attacker has standing to take over after the
current mandate's expiry. Mitigations: holder maintains keep-alive
discipline (renew before expiry); use multiple successors so a
single compromise doesn't grant unilateral takeover; rotate
successor sets in routine renewals.

**Genesis tampering.** The genesis mandate is trusted because the
consumer trusts the repo. If the repo's history is rewritten to
substitute the genesis, every consumer who has previously seen the
original genesis detects the substitution via cached state.
First-time consumers see whatever the repo currently shows; this is
the same trust property as `git clone` itself.

**Approval-rule downgrade.** A track's `policy.json` can change its
approval rule (e.g., from 2-of-3 to 1-of-N). Such a change is itself
a signed envelope that MUST satisfy the *current* rule; consumers
that have observed a stricter prior rule should warn on downgrade.

## 9. Compatibility and versioning

- Envelope `version` field is monotonically increasing within an
  envelope kind. v2 envelopes are accepted alongside v1 during any
  documented migration window.
- New envelope kinds are additive: implementations that don't
  recognize a kind MUST ignore it for authority decisions (consumers
  log the unknown kind but do not reject the track).
- New optional fields within an envelope are additive: unknown
  fields MUST be preserved during pass-through (e.g., when an
  adapter copies an envelope) but MUST NOT affect verification.
- Breaking changes require a v2 spec document and a coordinated
  migration window of at least 12 months during which both versions
  remain accepted by all major implementations.

## 11. Glossary

| Term | Meaning |
|---|---|
| Mandate | Time-bounded grant of signing authority on a track |
| Track | Independent timeline of mandates for a specific purpose |
| Holder | Pubkey currently authorized under an active mandate |
| Successor | Pubkey authorized to take over after the holder's mandate expires |
| Authority | The set of pubkeys currently authorized on a track |
| Endorsement | A signed declaration that a specific commit is a release |
| Intermediate commits | The list of commits between two consecutive endorsements |
| Adapter | Storage-layer plug-in (git or encrypted-blob) |
| Approval rule | Per-track schema for how many signatures are required |
| Takeover | A successor signing a new mandate after the predecessor expired |
